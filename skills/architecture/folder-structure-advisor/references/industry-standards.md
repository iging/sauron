# Industry-Standard Layouts

Many stacks ship a layout their tools expect. Build tools, test runners, and framework loaders read
these paths, so moving away from them breaks things or confuses every new contributor.

**Rule:** when the stack has an official or tool-enforced layout, start from it. Apply the generic
patterns in [the sample structures](sample-structures.md) inside it, for example feature folders
inside a framework's source root. Never rename a path the tool reads.

Each entry says whether the layout is **official** (the tool or language docs define it) or a
**community** convention (widely used, not enforced). Check the linked source for the current
version before you write a proposal, because frameworks change their defaults.

## Web frontends

### Next.js, App Router (official)

Source: <https://nextjs.org/docs/app/getting-started/project-structure>

```text
app/                   # Routes. A folder is a URL segment
  (marketing)/         # Route group. Parentheses keep it out of the URL
    page.tsx
  dashboard/
    _components/       # Private folder. Underscore keeps it out of routing
    layout.tsx
    page.tsx
  api/
    route.ts           # API endpoint
public/                # Static files served from the site root
src/                   # Optional. Holds app/ when you want config files apart
next.config.ts
```

Feature code can live beside its route or in `src/features/`. Keep `app/` for routing.

### Angular (official)

Source: <https://angular.dev/style-guide>

```text
src/
  app/
    users/             # One folder per feature area
      user-list.ts
      user-list.html
      user-list.css
      user-list.spec.ts
angular.json           # Angular CLI workspace settings
```

Group by feature, keep a component's files together, and put each test next to its code. Name a
component `UserList` in `user-list.ts`. The other files in `src/app/` come from `ng new` and change
with the CLI version, so read them from the project instead of copying them here.

### Vite with React (community on top of the official starter)

Source: <https://vite.dev/guide/>

```text
index.html             # Entry page. Vite expects it at the root
public/
src/
  main.tsx
  App.tsx
  features/
  shared/
vite.config.ts
```

### ASP.NET Core with Clean Architecture (community)

Source: <https://learn.microsoft.com/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures>

```text
MyApp.sln
src/
  MyApp.Domain/        # Entities and rules, no outside dependencies
  MyApp.Application/   # Use cases and interfaces
  MyApp.Infrastructure/ # Database and external services
  MyApp.Api/           # HTTP entry point
tests/
  MyApp.Domain.Tests/
  MyApp.Application.Tests/
```

## Languages

### Go module (official)

Source: <https://go.dev/doc/modules/layout>

```text
go.mod
cmd/
  api/
    main.go            # One folder per executable
internal/              # Code no other module may import. The compiler enforces it
  orders/
  storage/
```

Small projects can keep `main.go` at the root. Add `cmd/` once there is more than one program.

### Python package, src layout (official guidance)

Source: <https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/>

```text
pyproject.toml
src/
  my_package/
    __init__.py
    orders/
      models.py
      services.py
tests/
  test_orders.py
```

The `src/` folder stops tests from importing the local copy by accident.

### Rust with Cargo (official)

Source: <https://doc.rust-lang.org/cargo/guide/project-layout.html>

```text
Cargo.toml
src/
  main.rs              # Binary entry
  lib.rs               # Library entry
  bin/                 # Extra binaries
tests/                 # Integration tests
benches/
examples/
```

## Architecture styles

### Hexagonal, ports and adapters (community)

Source: <https://alistair.cockburn.us/hexagonal-architecture/>

```text
src/
  domain/              # Entities and rules. Imports nothing outside domain
  application/
    ports/             # Interfaces the domain needs, such as OrderRepository
    use-cases/
  adapters/
    inbound/           # HTTP, CLI, message consumers
    outbound/          # Database, payment provider, email
```

Dependencies point inward. Adapters depend on ports, never the reverse. See
[clean-architecture](../../clean-architecture/SKILL.md).

### Domain-driven design with bounded contexts (community)

Source: <https://martinfowler.com/bliki/BoundedContext.html>

```text
src/
  contexts/
    sales/
      domain/
      application/
      infrastructure/
    shipping/
      domain/
      application/
      infrastructure/
  shared-kernel/       # Small, agreed types both contexts use
```

One context per team language. Contexts talk through contracts or events, not shared tables.

## How to use this file

1. Find the project's stack in the approved context or its manifests.
2. Start from the matching layout. Cite its source in the proposal.
3. Apply one pattern from the decision matrix inside it, only where evidence supports it.
4. Record any deliberate departure from the standard layout as an open decision with a reason.
5. When no entry fits, say so and fall back to the decision matrix.
